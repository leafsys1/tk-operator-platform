## 0. 一句话

把「建任务」从**事后补规格**改成**先定义清楚**：左边跟 AI 对话说清要什么算子，中间实时长出**算子需求文档**，右边定**任务配置与精度方案**，点一下产出**任务上下文空间**；此后每轮开发都按清单把关键信息装进上下文。

## 1. 定位与入口

| 项 | 内容 |
|---|---|
| 位置 | IA 第八页（现七页见方案 §7）→ 插在「任务」之后，路由 `/tasks/new`；**不占侧栏常驻位**，入口 = 任务列表右上「+ 新建任务」+ 空态首屏 CTA |

| 与「对话」页的分工 | 对话页 = 任意长对话与历史；本页 = **一次有产出目标的受限对话**（产出物固定为 spec + 上下文空间） |

**现状差距（本页要补的）**：

- `POST /api/tasks` 现在只能建 `title / op_name / target_chip / input_form / criteria_ref`（`backend/app/schemas.py:263`）—— 没有执行机、镜像、设备、超时、预算；

- 前端没有任何创建向导页面（`web/src/App.tsx:7` 只有 `tasks / task / hosts / soon` 四个 view）。

## 2. 页面结构：单页三栏（**不做分步向导**）

```
┌ 任务开始 ─────────────────────────────────────────────────────────────── 存草稿 · 创建任务 ┐
│ ┌─ 需求输入 ─────────┐ ┌─ 算子需求文档（实时）──────┐ ┌─ 配置 / 精度 / 就绪 ────────┐ │
│ │ [自然语言|数学|代码]│ │ rms_norm · v1 · sha256 a8ad…│ │ 任务  项目/算子名/芯片      │ │
│ │                    │ │ ────────────────────────── │ │      执行机/镜像/设备       │ │
│ │ 💬 我要开发 rms_norm│ │ 来源 / 语义                │ │      超时/修复轮次/预算     │ │
│ │    做到跟 torch CPU │ │ 输入输出（shape·dtype）    │ │ ─────────────────────────  │ │
│ │    实现一一对应      │ │ 支持范围                   │ │ 精度方案                    │ │

│ │  ▸ dtype 支持哪些？  │ │ 版本与假设                 │ │ 就绪检查 7/7 ✅             │ │
│ │  ▸ eps 默认值？      │ │ ⚠ 待澄清 3 项              │ │ ─────────────────────────  │ │

│ │ [快捷句 chips]      │ │ [生成上下文空间]            │ │ [创建任务并生成上下文]      │ │
│ └────────────────────┘ └────────────────────────────┘ └────────────────────────────┘ │
```

**为什么不分步**：这页的核心动作是「说一句 → 立刻看到规格长了什么 → 同时看到配置与精度方案被怎么定」。分步会把对话打断，也让"我说的是 torch CPU 一一对应"与右侧「精度方案」的联动不可见。

### 2.3 创建流程与草稿生命周期（2026-10-15 定）

**四问已拍**：① 草稿**首次输入即自动建**（不是进页面就建空行，也不是只在点「存草稿」时才建）；② 上下文空间**最终确认时一次性落盘**（草稿期磁盘上不建空壳）；③ 本页**是新建流程的入口，但不做 app 默认落地页**（默认首页仍 = 任务列表）；④ 实现顺序 **先草稿生命周期、后对话式解析**。

**两层概念（别混）**：

| 层 | 是什么 | 何时出现 | 载体 |
|---|---|---|---|
| **草稿任务** | 一条 DB 行，`tasks.is_draft=1` | 首次输入 / 改配置时 `POST /api/tasks` | 后端；承载「临时保存 / 重新加载」 |
| **上下文空间** | 磁盘目录 `tasks/<slug>/`（TASK.md / AGENTS.md / context.yaml / spec/） | **最终确认**时一次性落盘 | 文件；slug 与内容都依赖定稿，草稿期不建 |

**状态机**：

```text
任务列表 ──「+ 新建任务」──▶ /tasks/new（前端态，尚无草稿）
   │ 首次输入 / 改配置
   ▼  POST /api/tasks  (is_draft=1)
草稿任务 ◀── 自动保存 PATCH /api/tasks/{id} ──▶ 重新打开 ?id=… 回填并续聊
   │ 对话：POST /api/tasks/{id}/parse → spec 草稿 + 待澄清项
   │ 逐项点闭合 → PUT /api/tasks/{id}/specs（新版本）
   │ 确认任务名 / 配置 / 精度方案 / 性能要求
   │ 前置门禁：待澄清 = 0 且就绪 7/7
   ▼  「确认并创建」
正式任务（is_draft=0 · stage=需求与设计）+ spec v1 + 上下文空间 tasks/<slug>/
   ▼
任务详情（作业台）
```

**「最终确认」= 显式定版门禁**（不是随手点一下）：

- 前置：待澄清项清零（主按钮沿用现有 `pending>0` disable）+ 就绪检查通过（§5.3）；
- 动作：先落库（`spec_versions` v1）→ 再写盘（上下文空间）→ 草稿转正（`is_draft=0`，`stage=需求与设计`）→ 跳任务详情。写盘顺序遵循 §6「先库后盘」；
- 定版后再改需求 → 走「另存为新版本」（方案 §4.4），**不原地改**。

**「性能要求」这个确认项的口径**（防与已定决策打架）：方案 §11.1 已定「不以获得性能提升为必需验收 / 不设加速比硬线」⇒ 本页的性能要求只收三样：① **基线选谁**（同条件）② **可选目标**（**允许留空**）③ **代表用例与测量条件**。**不做成「必须 faster」的硬门槛**。

**实现顺序（先低风险、后高不确定）**：

1. **草稿生命周期**（纯 CRUD，先让页面「活」）：`tasks.is_draft` 列 + 迁移；`POST /api/tasks` 扩字段（host_id / image_id / device_id / timeout_s / 预算）；`PATCH /api/tasks/{id}` 自动保存；前端去假数据、接后端、`?id=` 重新加载。
2. **对话式澄清**（需 LLM）：**已落并闭环**（2026-10-15）—— 走 **dsh 会话**（`POST /api/tasks/{id}/chat`，`--session-id` 续轮；曾短暂直连 opencode-go，已换回），逐轮产出「回复 + 规格草稿 + 待确认项」；业务证据落 `tasks.spec_draft`、过程落 `tasks.chat_log`；收尾 `POST /finalize`（定版门禁 → `spec_versions` v1 → `/context` 生成上下文空间 → 草稿转正）。**逐 token 流式已并入**（见下「对话输出契约」），就绪检查复用 `POST /actions` 的 `dry_run` 仍待接。

- **对话区**：消息流复用现有 SSE 呈现（`GET /api/agent-jobs/{id}/events`，已有），不新造一套对话内核。
- **快捷句 chips**（把常见意图变成一键，减少 token 往返）：
  - `跟 torch CPU 实现一一对应`（= 三块精度方案一次定，见 §5.2）
  - `按官方精度判据档` / `输入输出 shape·dtype 我另附`
  - `先只做 fp16 与 fp32，bf16 再说`
- **附件/贴板**：贴参考代码 `.py`、shape 表、现成用例 `cases.json`。
- **触发「解析需求」** → agent 产出 **spec 草稿 + 待澄清项**（方案 §4.2：关键语义未定不进入依赖它的代码生成）。
- **交互规矩**：待澄清项在中栏高亮，点它就在左栏被回答（一问一答就地闭合）；每轮结束必须给"还差什么"，**不开开放式闲聊**。

**示例（用户原话的那种）**：
> 用户：「我要开发 rms_norm，做到跟 torch CPU 的实现一一对应」
> → 已定：语义（按最后一维均方根归一化）、输入输出（x: [B,S,H] → y 同 shape）、参考实现（torch CPU）
> → 待确认：① dtype 支持集（fp32/fp16/bf16）② eps 默认值 ③ 是否支持 2D 以上按末维归约
> 用户三点勾选 → 待澄清清零 → 规格可定版。

### 3.1 对话输出契约（流式，2026-10-15 并入）

**为什么要有契约**：这页要「边说边出字」（打字机），而结构化产物（规格草稿 + 待确认项）必须机器可读。让模型只输出 JSON 就会把 `{"spec": ...` 一排字符喷到气泡里；只输出散文又丢结构。所以定成**两段式**：

```
<给用户看的自然语言回复 —— 逐 token 上屏>
<<<SPEC>>>
{"spec": {...}, "questions": [{"id":"q1","text":"..."}], "ready": false}
```

- **第一段 = `reply`**（写进 `chat_log`，就是用户看到的那些话）：分隔符之前的一切，前端逐 token 累加即打字机。
- **第二段 = 结构化产物**：`spec` / `questions` / `ready`，只落库、不上屏。
- **`ready` 仍是定版门禁的唯一开关**（`/finalize` 见 §2.3）。

**数据通路（一步不多）**：

| 环节 | 实现 |
|---|---|
| 模型输出增量 | dsh 侧 `opx-typewriter` 插件 hook `agent/assistant-stream`（官方扩展点）→ POST `OPX_DELTA_URL` |
| 收增量 | `POST /api/agent-jobs/{job_id}/delta`（`backend/app/routers/runs.py`）→ 写进该 job 的 `JobState` |
| 切分 | `backend/app/services/prose_relay.py`：`prose` / `tail` / `suppress` 三态状态机，逐段吐出「可上屏的 prose」并吞掉 JSON 尾（含分隔符被切成两半的防抖） |
| 送到前端 | 复用**已有**的 `GET /api/agent-jobs/{job_id}/events`（SSE）：`{"type":"delta","text":...}` 是正文增量，`thinking`/`status`/`tool_call` 是过程事件 |
| 跑完落库 | `_apply_parsed` → `chat_log` 里 assistant 的 text **= 流中那段 prose**（逐字一致，已实测） |

**兜底（必须有）**：插件是 dsh 开发者预览期的扩展点，可能变。所以——

- 起手判 JSON（模型退回旧格式）→ 判定 `suppress`，整段不上屏，跑完由解析器取 `reply` 补发；
- 一个 text 增量都没收到（插件静默/版本变了）→ 跑完把解析出的 prose **一次性补发**（`fallback: true`，不逐字但一定有答案）；
- 解析入口 `chat.parse_output()` **同时兼容旧格式**（整段一个 JSON、`reply` 在 JSON 里），历史对话与模型不听话都不会炸。

**总开关**：`OPX_CHAT_STREAM=0` 关掉插件挂载（退回「过程流式 + 兜底补发」）；插件端点地址 `OPX_DELTA_BASE_URL`（默认 `http://127.0.0.1:8077`，本机回环）。

**实测（2026-10-15，真 dsh + 真模型）**：单轮 88~99 段增量 / prose 449~471 字 / **零 JSON 泄漏** / 落库正文与上屏逐字一致 / 两轮 `dsh_session_id` 不变（续会话成立），第 2 轮 cacheRead 8064。

### 5.2 精度方案（三块；用户例子落这里）

| 块 | 选项 | 落到哪 |
|---|---|---|
| ① **参考实现（oracle）** | `torch CPU 实现（一一对应）` ★默认 · `numpy / 数学闭式` · `官方 aclnn 对应实现` · `任务自带参考代码` | spec「正确性·参考实现」+ 工作区 `references/`（`golden.py` 放这里） |
| ② **容差口径** | `ops-precision-standard@1`（官方档，带 sha256 指纹）★默认 · `自定义档`（per-dtype atol/rtol） | `tasks.criteria_ref`（**列已存在**）→ 判据档实体 `criteria/` |
| ③ **一致性口径** | ☑ 输出 **shape 与 dtype 完全一致** · ☑ 特殊值 NaN/Inf **逐元素精确比对**（不混进容差通过率） | 判据档正文 + 已有 `criteria/check.py` 的非有限值口径 |

**"跟 torch CPU 实现一一对应"这一句要拆成三个约束**（否则它只是句口号）：① oracle = torch CPU；③ shape/dtype 完全一致；并写进 spec「交付·调用形式」—— 广播规则、边界（空/单元素）、异常行为都要与 torch 语义对齐。
页面上这句话做成**一个预设 chip**：点一次把三块一起定，用户不必逐项填。

**判据档不许手改**：`criteria/ops-precision-standard@1/` 是官方 `mixed_tolerance_check.py` 的逐字节副本（带 PROVENANCE 与指纹），自定义档必须**换新版本号**。

## 8. 上下文装载契约（"每次把关键信息加载到上下文"）
