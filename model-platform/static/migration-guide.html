01迁移到底在做什么

一句话：让一个原本为 GPU/CPU 写的模型，能在昇腾 NPU 上真正跑出结果——而不只是"报错变少"。

迁移不是一件事，是四件事

层次要解决的问题典型症状
能装上依赖、Python 版本、wheel 有没有 aarch64 构建No module named X、No matching distribution
能加载建模代码在哪、类怎么构造、权重键名对不对Unrecognized model、size mismatch、missing keys
能算算子有没有 NPU 实现、有没有回退aclnn 报错、Unsupported op、静默 NaN
能交付别人换台机器照着能不能复现"我这能跑"但拿不到产物

最容易犯的错：把"跑起来了"当成"迁移成功"

最常见的是 model.to("npu") 不报错就宣布完成——但实际可能悄悄回退到 CPU， 或者权重根本没加载（strict=False 吞掉了几十个 missing_keys）。 本文后面第 8 节给了明确的判定标准。

02七阶段流程

每个模型都走同一条主线。有配方的走快路径（跳过 3–5），没有的走全流程。

01解析模型身份org/name → 本地目录；没有就下载
02选择迁移方案命中已验证配方 → 复用；否则逐步探路
03准备运行环境镜像、依赖、NPU 兼容层
04适配代码算子改 device / 补算子 / 换实现
05运行推理验证真的前向一次，拿到输出
06冒烟测试产物完整性 + 判定
07生成交付产物打包成可复现的 tar

两条路径

路径触发条件耗时做什么
fast命中已验证配方~20 秒 直接复用历史加载路线 + 修复步骤，只做一次加载确认
slow首次迁移3–10 分钟 画像 → 探路（20+ 条路线依次试）→ 报错归因 → 修 → 再试

为什么"配方"是核心资产

第一次迁移要花几十分钟试错，但试通之后把路线 + 依赖 + 修复步骤存下来， 下次同样的模型（或同家族模型）只要 20 秒。

03四步循环方法论

面对一个报错，不要靠灵感。按这四步走，每一步都有明确产出。

① 探路原样跑官方代码，只切设备。收集真实报错队列，不预判、不改造。
② 归因按证据特征分到 A/B/C/D/E 桶。看的是"这段报错长什么样"，不是记忆中的报错串。
③ 修复按桶选修法：补依赖 / 打补丁 / 换路线 / 写入口 / 通算子。
④ 回写修通了立刻写进坑库 + 生成配方。不写 = 下次还得重来。

三条铁律

铁律一：先建立"失败基线"。原样跑一遍拿到真报错，比凭经验猜改哪里快十倍。 很多"迁移难题"其实是自己提前改代码引入的。
铁律二：一次只改一个变量。同时改三处，成功了你不知道是哪处起作用，失败了你不知道是哪处害的。
铁律三：报错的第一行 ≠ 根因。调用栈指向的那个算子，往往只是"第一个做同步/搬移的调用点"， 真正崩的地方更早埋下。修不到点子上时，用最小复现脚本往前追。

一个非常常见的误判

「这个库不可用」—— 先确认它到底是哪个库

PyPI 上同名不等于同一个项目。实测踩过的：

包名你以为的实际装到的
cosyvoiceCosyVoice 模型代码只有 api.py/server.py 的 API 客户端（4 个文件）
ofaOFA 多模态模型Once-For-All 剪枝框架
janusJanus 多模态异步队列库
sapiensMeta 人体视觉抗体语言模型

判据：装完数一下文件数。pip show 说装了但 ls site-packages | grep <pkg> 只有 *.dist-info → 空壳 wheel。

另一个反直觉的规律

「缺什么」经常是假的 —— 先去查「是不是其实已经有了」

实测被推翻过的判断：

  • TripoSR 判"缺 DINOv2 权重" → 真因：权重本来就在 model.ckpt 里，只缺一份 config
  • megatron-util 判"PyPI 没有" → 真因：装了，但目录名带连字符（megatron-util vs megatron_util）
  • SwissArmyTransformer 判"已安装" → 真因：wheel 是空壳，只有 dist-info
  • GLM-Summarization 判"FFN 尺寸不对" → 真因：把 GLU 判反了（上下投影维度相等 = 非 GLU）

路线不是"选一个"，而是"依次试到通"

探针里每条路线都包在 try/except 里，失败就换下一条。 这也是为什么一个模型能试十几分钟——但换来的是不需要人肉试错。

05坑库：五桶归因

看到一条报错，先判断它属于哪一类。分类对了，修法就定了。

桶含义判据（证据特征）修法方向
A环境 / 依赖 ModuleNotFoundError、No module named、cannot import name 补装；必须带版本约束（numpy<2 等），否则带崩 NPU 栈
B设备 API device should be either、CUDA、.cuda()、npu_available 启用 NPU 兼容层（transfer_to_npu + verify_device 补丁）
C算子缺陷 aclnn、AscendC、not implemented、Unsupported op 算子桥接（复用 aclnn / 写 AscendC / 纯 PyTorch 替代）
D性能资源 out of memory、OOM、HBM、timeout 降 batch / 换空闲卡 / 数据并行
E结构与入口 Unrecognized model、no file named、size mismatch 换路线 / 写专用入口 / 从权重反推架构

A 桶：环境与依赖

看起来最简单，实际上最容易把人带沟里。核心难点是 "装得下"不等于"装得对"。

现象真相做法
PyPI 没有 aarch64 wheel官方源可能有 加 --extra-index-url（如 PaddlePaddle 官方源有 cp312-linux_aarch64）
PyPI 包名相同可能是另一个项目数文件数；看 config.yaml 里 !new: 引用的模块路径存不存在
pip show 说装了但 import 失败空壳 wheel只有 dist-info 没代码 → 从源码仓库装
包能装但 import 不了目录名带连字符ln -s megatron-util megatron_util
pip install 卡住依赖回溯爆炸--no-deps + 逐个补 ModuleNotFoundError

A 桶最危险的一条：装依赖带崩整个 NPU 栈

无条件装最新版 numpy / pyarrow 会让 torch_npu 直接不可用。 补装必须带版本约束，并且优先用 --no-deps 只装缺的那个包。

B 桶：设备 API

昇腾最有效的一招：torch_npu.contrib.transfer_to_npu 把 torch.cuda.* 全重定向到 torch.npu.*。 但还有一些它管不到的：

  • assert device.type == "cuda" 这类硬断言 → 补丁改断言
  • torch.cuda.is_available() 在自定义代码里 → 走 shim 兜底
  • torch.jit.script → NPU 不支持，要 TORCHDYNAMO_DISABLE=1
  • torch.compile(fullgraph=True) → NPU 上 InternalTorchDynamoError，关掉

C 桶：算子缺陷

这一桶最麻烦，因为报错位置常常不是根因。

场景做法
算子完全没有纯 PyTorch 等价实现（如 torch_scatter → 用 index_add 写）
算子有但精度不对定位到具体 op，看是否 fp16 溢出
C++ 扩展编译不过看它被调用的位置：只在导出/可视化用 → 写占位 stub

判断「C++ 扩展能不能 stub」的方法

看它在仓库里被调用的位置。只出现在"最后一步导出"就可以 stub；参与前向计算就不行。

实测可 stub 的：torchmcubes（只导出 mesh）、rembg（只抠图预处理）、 open3d（只可视化）、FlexiCubes（只提 mesh）。

D 桶：性能与资源

  • 910B1 单卡 64 GB HBM（npu-smi 报 65536 MB）
  • 模型权重超过 8 卡合计 512 GB → 直接判定无法迁移，不必尝试
  • 单模型未超限但多任务并发 → 排队，不要硬塞

E 桶：结构与入口

这一桶占比最高，也是最需要"看懂模型"的地方。

现象真相 / 做法
Unrecognized model缺 model_type 或需要厂商代码 → 换 pipeline / 写专用入口
size mismatch构造参数不对 → 去仓库找 config.yaml / models.yaml，别猜
missing_keys 一堆键名映射问题 → 按后缀匹配 + 形状校验
声明的类在仓库里不存在checkpoint 比公开代码新 → 从权重反推架构自己实现

E 桶最重要的能力：从权重反推架构

当官方代码不可得时，权重本身就写满了架构信息。看键名和形状就能复原：

word_embeddings.weight              → vocab, hidden
transformer.layers.N.*              → 层数
dense_h_to_4h vs dense_4h_to_h      → 是否 GLU（相等=非GLU，两倍=GLU）
attn.wk.weight 的形状                → 是否 GQA（比 wq 窄 = 有 KV 头分组）
rope_embed.periods                  → 用 RoPE 而非绝对位置编码

GLU 判据（卡过两轮）：dense_h_to_4h 与 dense_4h_to_h 维度相等 → inner_hidden_size = 4*hidden, no_glu=1；两倍关系 → inner = 2*hidden, no_glu=0。

06五类模型，差在哪

同样是"迁移"，五类模型的主战场完全不同。下面每张卡里的"最常见坑"都是实测频率最高的。

自然语言处理 38/38

成功率 100%

最成熟的一类。transformers 覆盖绝大多数， AutoModel 一把过。

  • 主战场：config 兼容、分词器、tie_word_embeddings
  • 最常见坑：lm_head.weight 缺失（其实与 embed 绑定）
  • 特殊：GLM 系走 SAT + Megatron 格式

计算机视觉 19/21

成功率 90%

分裂成两派：标准骨干（好迁）和带前后处理的业务模型（麻烦）。

  • 主战场：timm/OpenMMLab 权重、图像预处理、mesh 导出
  • 最常见坑：缺系统图形库 libGL.so.1
  • 特殊：3D 生成模型要 torchmcubes（可 stub）

多模态 24/28

成功率 86%

最难的一类。往往不是一个模型，而是多个子模型拼成的管线。

  • 主战场：子模型拆分、auto_map、双塔对齐
  • 最常见坑：auto_map 带 owner/repo-- 前缀，离线必炸
  • 关键心态：别想整体加载，逐个模块加载逐个验证

语音 19/20

成功率 95%

框架极度分散：SpeechBrain / FunASR / FishSpeech / CosyVoice / pyannote…

  • 主战场：每个框架一套加载方式
  • 最常见坑：官方提示"pip install modelscope[audio]"是误导，真因是缺 funasr
  • 特殊：FFT/STFT 类算子要验证 NPU 实现

科学计算 8/10

成功率 80%

科研仓库，接口最不统一。ai4s/* 系列小而简单， 蛋白质/气象类复杂。

  • 主战场：依赖链、数据加载、Paddle 框架
  • 最常见坑：config 在模块级读数据文件，没有数据就 import 失败
  • 特殊：HelixFold3 走 Paddle-on-NPU

跨类的共同点

不管哪一类都成立
  • 先解决"加载"，再谈"前向"，最后才谈"精度"
  • 官方 README 的安装说明常常是错的/过时的
  • strict=False 是掩盖问题的最快方式，别用

不同类别的"迁移成本"直观对比

类别首次迁移耗时主要时间花在复用后
NLP1–3 分钟下载权重~20 秒
CV2–6 分钟装依赖、找权重~20 秒
语音3–10 分钟认框架、补依赖链~30 秒
多模态5–20 分钟拆子模型、找构造参数~1 分钟
科学计算2–8 分钟依赖、数据、特殊框架~30 秒

这七个案例的共同教训

"某个依赖拿不到"这句话，在下结论前至少要验证三件事：

  1. 它是否真的不在包里（去翻 checkpoint 的键）
  2. 它是否真的不在 PyPI（换个名字查、查官方源）
  3. 它是否真的必需（看它被调用的位置，可能只是导出阶段）

我在这个项目里因为跳过这三步，至少误判了 6 次。

08什么算迁移成功

判定标准必须提前定死，否则会不断降低标准说服自己。

三级判定（本项目实际采用）

级别判定证据
LOAD-OK本项目的"迁移成功"标准 权重全部加载到位（missing_keys 清零或可解释）+ 在 npu:0 上真的前向一次拿到输出
SMOKE快速自检 小参数前向能跑通、产物落盘。用于验证环境，不比对数值
未验证不算成功 "能 import"、"能 to(npu)"、strict=False 吞掉一堆 missing —— 都不算

本项目的诚实边界：没有做数值精度对齐

所有 108 个模型的结论都是"能在 NPU 上加载并前向"， 不是"输出与 GPU 逐位一致"。原因是没有 GPU 基准输出可比。

所以本文所有"成功"都指 LOAD-OK，不指数值等价。这一点必须写清楚， 否则交付出去会误导使用者。

三条必须遵守的判定纪律

不要用 strict=False 掩盖问题。它会安静地吞掉几十个 missing_keys， 模型照跑但结果是随机的。允许用它，但必须把 missing 数量打出来并逐个解释。
必须在 NPU 上真的前向一次。只做 model.to("npu") 什么也证明不了—— 参数搬过去了不代表算子能跑。
不报错 ≠ 跑对了。NPU 上出现过静默输出 NaN、输出全零的情况。 至少检查输出 shape 合理、dtype 正常、不是全零。

怎么验证"真的能复现"

最强的一条：把交付包拿到干净环境里跑一遍。本项目实测过：

tar -xzf ai-modelscope-bert-base-cased.tar.gz
cd ai-modelscope-bert-base-cased
MODEL_DIR=/data/model_corpus/nlp/AI-ModelScope__bert-base-cased ./run.sh smoke

# 输出
VERDICT=LOAD-OK  2.6s  device=npu:0
[run] 完成。产物: .../output
EXIT_CODE=0

09交付物规范

迁移做完不等于交付完成。交付的定义是：别人换台机器、换个目录，照着就能复现。

一个模型一个自包含 tar 包

<包名>/
├── DEPLOY.md              部署报告（怎么部署 + 怎么判定成功）
├── TEST_REPORT.md         测试报告（测了没、过没过、实测数据）
├── ADAPTATION.md          迁移根因（为什么这么改，救援过的模型才有）
├── entry.py               模型专用入口
├── npu_shim.py            NPU 兼容层（必须随包，不能依赖外部）
├── run.sh                 一键复现（自动选空闲卡 + 完整/冒烟两种模式）
├── validate_delivery.py   验收脚本
└── weights_manifest.json  权重清单（文件名 / 大小 / sha256）

五条硬规则

规则为什么
权重不进包动辄几十 GB。用 MODEL_DIR 环境变量指向，包只带清单和 sha256
路径全用相对run.sh 用 BASH_SOURCE 定位自身， 包被拷到任意目录都能跑。写死绝对路径 = 换台机器就废
自动选卡遍历 0–7 找第一张无进程的卡。写死卡号到别人机器上必然撞车
镜像 tag 显式run.sh / DEPLOY.md 必须指向同一个 name:tag。 含糊的 tag 在异地会静默跑错版本
产物可判定跑完必须留下 entry_result.json 之类的东西， 含 loaded / forward_ok / device / 参数量的实测值

跑完留下的产物长这样

{
  "model": "AI-ModelScope/bert-base-cased",
  "route": "transformers",
  "device": "npu:0",
  "n_params": 108310272,
  "weight_dtype": "torch.float32",
  "loaded": true,
  "forward_ok": true,
  "forward_sig": "input_ids",
  "elapsed_s": 2.6
}

为什么交付物要强调"规则"而不是"现场"

写"我在 3 号卡上跑的，耗时 2.6 秒"对别人没用。要写成规则： "遍历 0–7 找第一张无进程的卡"、"遍历 NPU 卡，取第一张空闲的"。 现场数据放 TEST_REPORT.md 留档，通用规则放 DEPLOY.md 作为约定。
